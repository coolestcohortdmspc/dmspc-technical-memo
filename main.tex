\section{Design Decisions} \label{Design Decisions}

\subsection*{Desktop Application versus Web Application}
  To enable system communication across NRAO sites, the software needs to be compatible with various types of machines and operating systems. For use in ngRadar, the software would need to communicate across the continental United States, Hawaii, and the Caribbean.
    
  An initial investigation was completed to evaluate the viability of developing locally installed desktop applicatons, which would transmit data over the internet to software at other locations. However, this would have required compiling and building an application for all three major operating systems. Therefore, it was decided that the software would not be locally hosted, and instead function as a web application. This website would be primarily hosted on servers at DSOC, with other software components hosted at the Green Bank Observatory and on all ten of the VLBA sites. 

\subsection*{Backend Frameworks}

Three backend frameworks were investigated for this prototype - Flask, FastAPI, and Django.
  Flask is well-known for its simplicity and low usage of computing resources. It is also flexible and modular, allowing developers to modify the framework and integrate additional software components for added functionality. However, Flask only supports using synchronous communication between the server and framework, meaning processes can only run one-at-a-time. Flask also does not have built in authentication or adminstrative features.

  FastAPI provides high-speed, asynchronous, non-blocking communication in a relatively lightweight framework. It is the newest framework out of the three that were investigated and includes features such as built-in authentication, Python code completion to speed up development, and automatic documentation for program APIs. It includes a modest number of built-in functionality, and developers can add libraries with additional features they need.

  Django is a framework with a large amount of built-in functionality including an adminstrative dashboard, user authentication, HTML form processing, an object-relational mapper for database interaction, and a model-template-view architecture to seperate program logic from what the user can see. It is capable of running large web applications with many users. By default, Django runs with synchronous communication, but libraries that add asynchronous communication are avaliable.

  After considering all three frameworks, Django was chosen due to the large number of compatible software libraries, built-in security and adminstrative features, and its ability to scale as website traffic grows.


\subsection*{Message Brokers}

  Real-time data transmission across geographically separated locations was a defining requirement of this software prototype, and choosing a software tool to accomplish this was a major decision made early in the design process. Initially, socket programming was considered for communication over the internet, but the added complexity of developing original low-level code to do this reliably with multiple computers led to this idea being ruled out. The investigation then shifted course to researching existing message brokers to accomplish real-time data transmission.

Three message brokers were investigated - Apache Kafka, RabbitMQ, and Apache Pulsar. Apache Kafka was first released to the public in 2011, and is the most widely used message broker across the industry. It is best suited for high volume data transmission, and uses a central server known as a cluster, with one or more message brokers to handle requests from producers and consumers. Kafka uses "producers" to send messages to user-defined topics. Messages are stored in these topics in subgroups called partitions, either until consumption is confirmed or for a fixed amount of time. "Consumers" are used to receive messages from these topics. The initial time to implement a basic Kafka messaging setup is minimal; however, scaling up the system and debugging errors adds significant complexity. Kafka can also use more computing resources than necessary if only sending a small amount of data. However, Kafka is very reliable, and has several built-in methods to prevent data loss if servers crash. 

RabbitMQ was also considered as a broker option; it has the lowest message latency and lowest server memory requirement compared to the other two options, and is a significantly simpler system. This option was not chosen due to RabbitMQ's push model (producer controls the flow of messages and can overwhelm consumers) and the difficulty in scaling up the system. Apache Pulsar, the third option considered, is the newest of the three message brokers and attempts to combine the features of Kafka and RabbitMQ. Pulsar is well suited for scaling up to handle high volumes of data. However, with the extra features Pulsar offers, it is more complex to set up than Kafka, has a higher message latency due to the extra storage layers, and has less documentation avaliable.

  Ultimately Kafka was selected as the message broker for this prototype, as it has many highlights: extensive use across the industry, high reliability and customization when sending or receiving messages, and a large amount of documentation. One of the most important features of Kafka for this prototype is the publish/subscribe model, and the ability for multiple consumers to retrieve information from a single producer. 
  
  Kafka has numerous options for online broker hosting, and initially the website was set up to work with Confluent Cloud. However, locally hosted Kafka brokers were later chosen due to lower cost, increased flexibility, and more control over the data on those brokers.

\subsection*{Docker}

In this prototype, Docker containers were used to ensure that the software could be run across multiple machines for local development and debugging, but also perform reliably when run on a cloud-based or locally hosted server. Each of the major software components has its own container, which is known as the microservices architecture. This made development and deployment of the software more flexible, as the code for individual services could be changed without altering another container. It also helped separate the codebase into smaller pieces and made it easier to replace individual services in the code with alternatives if changes were necessary. Microservices also improved fault tolerance for the website - during testing, there were several times that a container had stopped working. This did cause some features to stop working correctly, but did not cause the website to crash as a whole.

Containerization ensures that any computer which has the Docker Engine - a server responsible for managing the containers - can run this web application with consistent performance.

\subsection*{Object Store}

  This software prototype simulates generating DDM images from the raw data generated by VLBA antenna stations. Storing these images directly in a database as binary files significantly reduces performance and increases database size when large numbers of images need to be produced. Using a dedicated object store means the database only needs to store text-based information, enabling faster database queries and the ability to serve images using SDKs such as AWS Boto3. 

    Three object stores were investigated: MinIO, Garage, and SeaweedFS. MinIO was first released in 2015 as an open-source object store, with features including an administration panel, data encryption and authentication, support for object version control, forward error correction, and optimization for parallel request handling. However, in late 2025, MinIO shifted to focus on commerical customers, and no longer maintains the open-source code. It can still be downloaded from GitHub, although some of its features have been removed, and users must build it from source now. Garage was investigated second as an object store option, and it is designed to be simple and use minimal computer resources. It offers a modest feature set, including data compression and backup, AWS Boto3 integration, and an online admin interface. However, to install and set up the software, it must be built directly from the source code, which would add time and complexity to the project. The last object store researched was SeaweedFS, a distributed storage system designed to handle large numbers of files and scale with linear efficiency. Some additional features include data protection, file recovery, efficient metadata management, flexible deployment, and compatibility with multiple storage volumes, including Boto3. The SeaweedFS code comes packaged as a binary file with a built-in installer and a setup guide for Docker, making installation easy. After installation, there are three major software components of SeaweedFS: the Master server, Volume servers, and the Filer server, which provides file system semantics. 

    SeaweedFS was chosen as the object store for this prototype because it is fully open source and actively maintained, it is easy to set up across multiple operating systems, performs well when used with large numbers of files, includes data protection features, and provides guides on how to set it up for Docker.

  

\subsection*{Data Movement}

  The first data transfer tool tested within this prototype was etransfer, which was developed by the Joint Institute for VLBI ERIC (JIVE) and has become the standard data transfer tool within the VLBI community. The code repository for this tool is free to use and open source, which benefits development by allowing for code adjustments as needed \cite{marjolein_verkouter_jive-vlbietransfer_2026}. Etransfer supports TCP, UDT, and SRT, with UDT and SRT being the recommended protocols. The etransfer client (etc) and etransfer daemon (etd) system allows the client program to initiate both client to server transfers and server to server transfers, with the latter option ensuring data does not flow through the client's machine or network (note that server and daemon are interchangeable). This tool supports resuming failed transfers, multiple transfers to one daemon in parallel, and access control lists to define allowed and denied directories. It does not yet support authentication and authorization.


  ExpeDat was the second data transfer tool evaluated for use in this website, and it was developed by Data Expedition, Inc. Unlike most of the other code in this prototype, it is proprietary and uses the Multipurpose Transaction Protocol (MTP), a data transport protocol which can adapt to changes in network conditions, and is based on the open-source User Datagram Protocol (UDP). The software consists of a server and several client applications to move files between networked computers. It is capable of resuming incomplete file transfers, compressing data before transferring it, tracking file upload status, and remotely monitoring the server status. These settings can be changed in the \textit{servedat.cf} and \textit{svpasswd} files. The client and server can be set up and installed on Windows, Linux, and MacOS, or configured to run inside a docker container.


\subsection*{Cloud-Hosting Solutions}

  While developing this website, there was a need to test the system communication between geographically distributed locations. If this software architecture was implemented to work with telescope hardware, it would be hosted using servers on site at NRAO locations across the country. The website could then be used to communicate between observatory sites, and inform remote viewers of real-time events during an active observation.

  There were two platforms chosen to host the website during this process, the first was Render and the second was DigitalOcean. Render offers a free option for hosting small websites with very limited performance - 1GB of storage, 256 MB of RAM, and 1/10th of a virtual CPU. This offered a way for the website to be tested over the public internet, but performance was very slow. Render offers paid subscriptions starting at \$7, but the least expensive plan which includes 1 virtual CPU is \$25 per month, and includes only 2GB of RAM. The limited performance and expensive cost of using Render led to exploring alternatives for this prototype.
  
  DigitalOcean is a cloud-hosting platform, which sells access to Linux-based virtual machines called Droplets. These are available for purchase at various locations hosted worldwide. After testing the performance of a single Droplet, further setup was completed to have Droplets on servers located in New York, San Francisco, London, Bangalore, and Sydney, running the website and its containers in a distributed, global environment. DigitalOcean offers Droplets with varying performance levels, and monthly subscriptions to four entry level droplets and one mid-tier droplet were purchased for prototyping. Each entry level Droplet offers 1 virtual CPU (vCPU), 2GB of RAM, 50GB of storage, and costs \$12 per month. The mid tier droplet has 4 vCPUs, 8GB of RAM, 160GB of storage, and costs \$48 per month. The portion of the website representing DSOC contains the software tools which managed the SQL database, Kafka brokers, data transport server, SeaweedFS file store, and various performance monitoring tools. To perform at an acceptable speed and support multiple website users, DSOC was determined to need this mid-tier droplet. The other portions of the website, including the GBT and VLBA simulators, were spread out evenly across the 5 Droplets. Since migrating the website to work on DigitalOcean, performance has significantly improved, even when many people are navigating it at once. Currently, this prototype website costs \$96 per month to operate on a cloud-hosted service, but that cost will only exist during the development phase.

\section{Software Stack} \label{Software Stack}
The System Communication Prototype was developed using a collection of open-source frameworks, containerization tools, messaging infrastructures, data storage technologies, and monitoring services. These technologies support the prototype's web interface, geographically distributed simulators, event-driven communication, data transfer operations, and performance monitoring.

\subsection*{Django-Based Web Application}
The ngRadar web application was developed using Python and Django, a high-level web framework that provides built-in functionality for URL routing, database integration, user authentication, and server-side HTML rendering. Django follows a Model-View-Template (MVT) architecture, in which models define the application's data structures, views handle incoming HTTP requests and application logic, and templates generate the HTML presented to users. The frontend was implemented using HTML, CSS, JavaScript, and Bootstrap, without introducing a separate frontend framework. Django templates render the application's pages, while JavaScript manages user interactions and dynamically updates the interface. Bootstrap provides reusable styling components and responsive page layouts.

The Django application runs using the Asynchronous Server Gateway Interface (ASGI), which supports asynchronous connections and long-lived HTTP responses. The prototype web application requires two Kafka consumers for updating the user interface via Server-Sent Events (SSE) to deliver real-time simulation updates from the backend to connected browsers. One Kafka consumer (UI consumer) runs within the website container, listens for simulation events, and forwards relevant updates to the homepage through SSE. A second Kafka consumer (database consumer) listens for the same events, but also persists a historical record of all events before first forwarding relevant updates to the history events page. This means that the homepage is fully decoupled from the database during an active simulated observation as Kafka event messages are forwarded directly to the homepage, and the history events page, while still coupled to the database, does not require constant database polling for new updates to the website. 


\subsection*{Docker Containerization}
All major components of the System Communication Prototype were containerized using Docker, including the GBT simulator, ten VLBA station simulators, DSOC simulator, Django website, Kafka infrastructure, PostgreSQL database, SeaweedFS storage services, and monitoring tools. The complete development and deployment environment consisted of approximately 34 containers, depending on the enabled services.

Docker Compose was used to define and manage the containerized environment through YAML configuration files. These configurations specify container images, build instructions, environment variables, startup commands, port mappings, volumes, and networking settings. Docker Compose also allowed the team to start, stop, rebuild, and recreate groups of related services during development and deployment. For ease of use, the team utilized a control script kept up to date with commands for common Docker invocations.

Containers running on the same Docker host communicated through Docker-managed bridge networks. Docker's internal DNS service allowed containers to reference one another using service names rather than fixed IP addresses. Communication between containers deployed on separate DigitalOcean Droplets used network-accessible host endpoints, protected by DigitalOcean's cloud firewall.

Docker volumes and bind mounts were used to persist application data and share directories between containers when necessary. For example, shared directories supported simulated observation data streaming, while persistent volumes were used for services such as PostgreSQL and SeaweedFS.

\subsection*{Apache Kafka Event Messenger}
Apache Kafka is a distributed event-streaming platform used to publish, store, and consume event messages between independent application components. Kafka organizes messages into topics, allowing producers to publish events and consumers to subscribe to the topics relevant to their processing responsibilities.

The prototype implemented a three-broker Kafka cluster using KRaft for cluster metadata management, eliminating the need for a separate Apache ZooKeeper service. Kafka brokers were deployed across multiple DigitalOcean Droplets. Supporting containers included Kafka UI, which provides a web interface for inspecting topics and messages, and a Kafka initialization service responsible for creating the required topics during environment startup.

 \begin{itemize}
  \item Four Kafka topics were used to coordinate the simulated observation workflow:
  \begin{itemize}
    \item GBT notif: Events associated with GBT waveform selection and transmission.
    \item VLBA notif: Events associated with VLBA station processing, storage requests, and data transfers.
    \item DSOC notif: Events associated with DSOC processing, storage responses, and observation completion.
    \item progress tracking: Progress updates associated with ExpeDat data streaming.
  \end{itemize}
\end{itemize}

The GBT, VLBA, and DSOC simulators communicate by publishing and consuming Kafka messages. For example, submitting a waveform through the Django website publishes an event to GBT notif, which is consumed by the GBT simulator. Subsequent messages coordinate the simulated transmission, VLBA processing, storage negotiation, data transfer, and DSOC processing stages.

Kafka messages use a common payload structure containing observation identifiers, station information, waveform metadata, processing status, timestamps, and other fields relevant to the simulation. As an observation progresses, producers populate additional metadata required by downstream consumers. Kafka message keys identify event types so consumers can distinguish actionable workflow messages from other notifications.

Two additional consumers support the website and database. The UI consumer subscribes to the simulation topics and forwards relevant events to the frontend using SSE, while the database consumer records simulation events in PostgreSQL for historical persistence. Both consumers operate independently of the observatory simulators.

Kafka is used to transmit event notifications and workflow metadata rather than large observation data files. The simulated scientific data is streamed separately using ExpeDat.


\subsection*{PostgreSQL Database}
The prototype uses PostgreSQL as its primary persistent database for application data and historical simulation events. The database runs in a Docker container and is accessed by the Django application through Django's Object-Relational Mapper (ORM).

Django models define the database structures used to represent observations, simulation events, station identifiers, processing statuses, and associated metadata. A dedicated database consumer subscribes to all four Kafka topics and persists simulation events to PostgreSQL as an observation progresses. These records include observation identifiers, event timestamps, station names, waveform selections, processing statuses, data streaming metadata, and latency measurements.

The Django website uses PostgreSQL to populate its historical observation interface. When the history page initially loads, Django queries the database to retrieve previously recorded events. During an active observation, the database consumer persists incoming Kafka events to PostgreSQL before publishing real-time updates through Server-Sent Events (SSE), allowing the history page to display newly recorded events without additional database polling or manual page refreshes.

Both the database consumer and the UI consumer utilize the same SSE broker and shared browser connection to deliver updates to their respective interfaces. However, their data handling differs: the homepage is completely decoupled from PostgreSQL and receives live simulation updates directly from Kafka through the UI consumer, while the history page relies on PostgreSQL for initial data retrieval and requires events to be persisted by the database consumer before corresponding SSE updates are delivered. This ensures that events displayed in the history interface have already been recorded in the database.


\subsection*{ExpeDat Data Streaming}
ExpeDat is a high-performance technology designed to deliver data efficiently across networks, including wide-area connections with significant latency. ExpeDat supports both file transfer and streaming capabilities with the only difference being the flag used in the CLI command. It provides an alternative to conventional file transfer or streaming mechanisms for applications that require high-throughput movement of large datasets.

The prototype used ExpeDat's data streaming feature to simulate streaming raw observation data from the VLBA station containers to the DSOC environment. Each VLBA simulator initiates a data streaming process after receiving the appropriate workflow notifications and confirmation that the DSOC environment has sufficient storage capacity.

The streaming process uses ExpeDat client and server components to send simulated observation data to a destination directory accessible to the DSOC simulator. This streaming progress is monitored and published to Kafka through the progress tracking topic, allowing the Django website to display progress updates for the remote observer regarding the individual VLBA stations' streaming progress.

After a data streaming process completes, the DSOC simulator verifies that the received data matches the expected data size before continuing its processing workflow. Kafka handles the control messages coordinating these operations, while ExpeDat handles the actual data streaming.


\subsection*{SeaweedFS - Object Store}
SeaweedFS is an open-source distributed storage system that supports file storage and object storage through an Amazon S3-compatible interface. Its S3 API allows applications to store and retrieve objects using standard object-storage operations.

The prototype uses SeaweedFS as an object store for the simulated Delay-Doppler Map (DDM) images generated by the DSOC simulator. SeaweedFS runs in the Docker environment and exposes an S3-compatible endpoint for application access.

After the DSOC simulator validates an incoming observation data stream, it generates a simulated DDM image and uploads the image to SeaweedFS. The resulting object key is included in the observation metadata and persisted in PostgreSQL, allowing the Django application to locate and display the generated image for that associated simulated observation event. SeaweedFS is used specifically for storing generated image products, while PostgreSQL maintains the associated structured observation metadata.

\subsection*{DigitalOcean Droplets}
DigitalOcean Droplets are Linux-based virtual machines hosted on DigitalOcean's cloud infrastructure. Each Droplet provides an independent computing environment with configurable CPU, memory, storage, and networking resources. The prototype was deployed across five DigitalOcean Droplets located in San Francisco, New York, London, Bangalore, and Sydney. Each Droplet hosted a subset of the Docker containers, distributing the simulated observatory processes across geographically separated cloud environments.

 \begin{itemize}
  \item The DigitalOcean cloud-hosted container distribution was set up as follows:
  \begin{itemize}
    
    \item San Francisco: GBT simulator, VLBA-BR, VLBA-MK, a Kafka broker, and a Portainer Agent.
    \item New York: DSOC simulator, VLBA-KP, VLBA-OV, the Django website and UI consumer, database consumer, PostgreSQL, SeaweedFS, Kafka infrastructure, ExpeDat server, Traefik, Portainer, and monitoring services.
    \item London: VLBA-SC, VLBA-HN, a Kafka broker, and a Portainer Agent.
    \item Bangalore: VLBA-NL, VLBA-FD, and a Portainer Agent.
    \item Sydney: VLBA-LA, VLBA-PT, and a Portainer Agent.

  \end{itemize}
\end{itemize}

The New York Droplet hosted the majority of the prototype's centralized services, including the public-facing website and UI consumer, database, database consumer, object storage, and observability infrastructure. The remaining Droplets primarily hosted the distributed GBT and VLBA simulation containers. Each Droplet has a Portainer agent which forwards container health metrics and control to a main Portainer container hosted on the DSOC droplet. Portainer is a container management platform that provides a web-based interface for administering Docker environments. 

Each Droplet maintained its own Docker environment, with communication between geographically separated services occurring over network-accessible endpoints. This configuration allowed the prototype to execute its simulation processes across multiple cloud regions while using centralized application and storage services. This deployment allowed the prototype's geographically separated simulation components to remain connected through the Kafka messaging infrastructure and ExpeDat data streaming services.

\subsubsection*{Traefik Reverse Proxy}
Traefik is an open-source reverse proxy and load balancer that routes incoming HTTP and HTTPS requests to backend services. It supports Docker integration, allowing routing configurations to reference containerized services.

The prototype uses Traefik to expose the Django website to the public internet. Traefik runs in a Docker container on the New York Droplet and forwards incoming website requests to the Django application running on the internal Docker network.

Traefik provides HTTPS termination and supports automated TLS certificate management through Let's Encrypt. Its Docker integration allows routing rules to be configured using container labels and service definitions.

Traefik also exposes Prometheus-compatible metrics, allowing request traffic and reverse-proxy performance to be monitored through the prototype's observability infrastructure.


\subsection*{Performance \& Monitoring Tools}
The prototype incorporates several monitoring and performance testing technologies to observe container health, collect application and infrastructure metrics, measure website performance, and trace processing operations across the distributed system.

Portainer allows users to inspect running containers, view logs, monitor resource utilization, and manage container lifecycle operations. The prototype uses a centralized Portainer instance hosted on the New York Droplet, with Portainer Agents deployed on the geographically distributed Droplets. The Agents provide remote access to their respective Docker environments through the central Portainer interface. This configuration allows the team to inspect container statuses, restart services, review logs, and monitor Docker resources across the distributed deployment without connecting individually to each Droplet.

Prometheus is an open-source monitoring system that collects and stores numerical time-series metrics. It periodically retrieves metrics from configured HTTP endpoints, commonly referred to as scrape targets, and stores them for querying and visualization. The prototype uses Prometheus to collect application, container, and infrastructure performance metrics. Exporters expose measurements from supporting technologies, including Kafka and PostgreSQL, in a format that Prometheus can scrape. The monitoring environment includes exporters for collecting information such as Kafka consumer lag, broker and topic statistics, database activity, and system resource utilization. Additional metrics from instrumented application components and Traefik provide visibility into application and HTTP request behavior. Prometheus serves as a metrics data source for Grafana, where the collected measurements are displayed in monitoring dashboards.

k6 is an open-source performance testing tool used to generate HTTP traffic and measure application behavior under simulated workloads. Tests are defined using JavaScript and can be configured with virtual users, iterations, execution durations, and performance thresholds. The prototype uses k6 to perform load testing against the Django web application. Test scripts simulate user interactions with the website, including authenticated requests, observation submission operations, and requests to application endpoints. The tests collect measurements such as HTTP request duration, request failure rate, response times, and successful request checks. Configurable thresholds allow the team to evaluate application behavior against defined performance targets. These measurements are used to establish a performance baseline for the website and identify potential bottlenecks as the number of concurrent requests or simulated users increases.

OpenTelemetry is an open-source observability framework that provides APIs, SDKs, and instrumentation tools for collecting telemetry data from applications. It supports distributed tracing, metrics, and logs. The prototype uses OpenTelemetry to instrument Python application components, including the GBT, VLBA, and DSOC simulators and Kafka-consuming processes. Instrumented operations generate trace spans containing information such as operation names, timestamps, execution durations, Kafka topics, message offsets, and processing statuses. Trace context is propagated through Kafka message headers so that processing operations across different containers can be associated with the same distributed trace. This allows individual workflow operations to be examined across producer and consumer boundaries. An OpenTelemetry Collector runs as a Docker service and receives telemetry exported by instrumented components using the OpenTelemetry Protocol (OTLP). The collector processes the incoming telemetry and forwards trace data to Grafana Tempo. Tempo is a distributed tracing backend that stores and retrieves traces. It is integrated with Grafana, allowing the team to inspect individual spans, trace execution paths, identify failed operations, and analyze processing durations across the simulated observation workflow.

Grafana is an open-source visualization and observability platform used to build dashboards from metrics, logs, and tracing data sources. It supports integrations with Prometheus for time-series metrics and Tempo for distributed tracing. The prototype uses Grafana as its central interface for viewing system performance and observability data. Grafana dashboards display metrics collected by Prometheus, including infrastructure resource utilization, Kafka activity, HTTP request performance, and application measurements. Grafana is also connected to Tempo, allowing distributed traces generated by OpenTelemetry instrumentation to be inspected through the same interface. Trace views provide visibility into processing operations performed by the individual simulators and Kafka consumers. Custom dashboards organize these measurements by application component, providing a centralized view of the prototype's operational behavior and supporting performance analysis during development and testing.

\section{Dependencies} \label{Dependencies}

  This section describes the dependencies required for the System Communication Prototype to function properly. These dependencies include software libraries, external services, and hardware requirements. The versions are a snapshot as of October 2026. Sources are \texttt{requirements.txt}, \texttt{Dockerfile}, \texttt{docker-compose.yml}, and the running containers. The only proprietary or licensed dependency is ExpeDat. Some versions are not fixed in those files, so a rebuild may install different versions than the ones listed here.

\subsection*{Language and Runtime}

  The chosen language is Python because the prototype involves a large amount of data transfer and management. Python is also widely used across astronomy, all team members have prior experience coding in it, and the website does not require the extra computing speed offered by compiled languages such as C++. All components are containerized in Docker to simplify compatibility. The version is Python 3.11 (the \texttt{python:3.11-slim} base image, running 3.11.15).

\subsection*{Web Framework and ASGI}

  ASGI is the modern standard for Python web applications that support asynchronous programming, while WSGI is the classic standard for synchronous, blocking web applications. ASGI supports async views and server-sent events (SSE). SSE pushes updates to the browser as they happen, replacing the database polling used early in development, which became a performance bottleneck. Uvicorn is used to run the ASGI application. Django is constrained to \texttt{>=5.2,<5.3}.
Django is constrained to run versions greater than or equal to 5.2 through 5.3.

\subsection*{Kafka}

  There are three brokers in KRaft mode, so that if one is down, the others can stay up. The JMX exporter is used as a Java agent to expose broker metrics to Prometheus, so that they can be shown on the Grafana dashboard. The one-shot \texttt{kafka-init} container, built on the cp-kafka image, creates the topics. The Python client is confluent-kafka, built on librdkafka.

\subsection*{Database and File Storage}

  PostgreSQL is used for the database, with psycopg, psycopg-binary and postgres-exporter. SeaweedFS is used for image storage, with boto3 and botocore to communicate with the S3 gateway. To generate simulated DDM images, numpy, pandas, matplotlib and pillow are used, with some supporting libraries: argon2-cffi, argon2-cffi-bindings, cffi and pycparser.

\subsection*{Data Movement}

  The prototype experiments with two data transfer tools: etransfer and ExpeDat. Etransfer (v2.0, from JIVE) is free and open source, so it is compiled from source at build time. It needs a C++11 compiler, bundles its own UDT and SRT libraries, and listens on port 4004 for commands (TCP) and port 8008 for data (SRT). ExpeDat (\texttt{servedat} 1.23.1, MTP 4.5.3) is proprietary: the vendor ships ready-made binaries, which are copied into the image at build time, with separate arm64 and x86-64 builds. The free trial is valid for 21 days, so production use would need a license.

\subsection*{Testing and Load Testing}

  Pytest, pytest-django, pytest-cov and pytest-asyncio are used for the testing environment, and k6 is used for load testing in its own container.

\subsection*{Infrastructure and Monitoring}

  Traefik is used to handle HTTPS and UDP routes. Docker Desktop and Compose are used on the development machines. Portainer, Prometheus and Grafana use latest-tag images.

\subsection*{Hardware and Hosting}

  The project is deployed on DigitalOcean. There are four droplets with 1 vCPU, 2 GB RAM and 50 GB disk for GBT and VLBA, and one droplet with 4 vCPU, 8 GB RAM and 160 GB disk for DSOC, where the database, image storage, ExpeDat server and other containers are hosted. Note that development is on arm64 (Apple Silicon) while the droplets are x86-64, so the binaries must match.

\section{Ideas for Future Improvements} \label{Future}


  The prototype demonstrates the full event flow, and the items below are what remain for a production-ready ngRadar system. The section is organized as known issues, improvements, and features.

\subsection*{Known Issues}

  The submit new waveform button unlocks after the first of several concurrent VLBA transfers completes, rather than after all of them have completed. A new waveform can therefore be submitted while earlier transfers are still running. The button should stay locked until every transfer in the sequence is complete.

  Part way through the prototype's development, a large refactor decoupled the UI from the PostgreSQL database and made the UI completely event-driven, relying on Kafka for updates instead of polling the database. Before this refactor, certain safeguards ensured that the website, backend processes, and Docker ecosystem could fail gracefully and print helpful logs for debugging and restarting, rather than failing and exiting. None of these graceful failure scenarios have been tested since the UI bridge refactor. Going back through those scenarios would confirm that the prototype still fails gracefully.

  The \texttt{vlba\_sim} container stops reading Kafka for up to 15 minutes while it waits for the daemon after an outage. A waveform submitted during this time sits unprocessed until the wait resolves. Reading Kafka messages while waiting would remove this delay.

  The \texttt{-6} return code cannot separate a stopped daemon from network loss, so the error message cannot name the cause. The message describes what the code means (a connection or write failure), not a guaranteed root cause.

\subsection*{Improvements}

  Moving from cloud hosting to in-house infrastructure is worth evaluating. The main reason is full control over the sequence of events, with the ability to configure the servers, network, and services however the project requires. The cloud droplets also limit the available CPU, RAM, and storage. The trade-offs are cost, maintenance, reachability from VLBA sites, and security.

  Kafka runs out of memory on the 2 GB droplets. Each node uses about 800 MB of RAM, and with no swap configured, the Linux out-of-memory killer stopped two of the three Kafka nodes. The fixes are more RAM or a swap file, and restart policies on the Kafka containers.

  The capacity of the data transfer path is not yet characterized. Concurrent overlap of transfers was never measured, and no real-network bandwidth or latency numbers exist. During testing, a limit on the number of concurrent transfers was suspected, but there is no direct proof of one. If such a limit exists, it could come from the resources retained on the droplet rather than from ExpeDat itself. Measuring CPU, RAM, and disk usage with the existing Prometheus and Grafana dashboards while increasing the number of simultaneous transfers would show which.

  The shared volume needs periodic cleaning, because repeated runs can exhaust the simulated 5 GB.

\subsection*{Features}

  Originally, DSOC checked its storage and responded to a single VLBA station about whether it could accept the incoming etransfer or ExpeDat raw data transfer or stream. Currently, this check occurs simultaneously for all 10 VLBA stations. With 10 consecutive storage check requests, DSOC responds yes without accounting for the requests it has already approved, so with simultaneous transfers or streams, DSOC storage could exceed its limit for incoming raw data. DSOC should keep a running storage count, updated before and after each approval of a VLBA site's incoming transfer or stream.

  On the history events page, DSOC sends a ``Completed'' Kafka message 10 times for the 10 VLBA simulators. DSOC should instead wait until all 10 VLBA raw data transfers are processed and the 10 DDM images are generated and stored in SeaweedFS, and then send a single ``Completed'' message. This message is displayed on the UI and tells the remote observer that the sequence of events has finished.

  Observer notifications would alert a remote observer when a sequence completes or fails, so the history page does not need to be watched continuously. Because every event already passes through Kafka, a new consumer could subscribe to the existing topics and send an email or chat message when it sees a completion or failure event.

  User roles would separate what observers and operators are allowed to do. For example, observers could view the home and history pages, while only operators could submit a new waveform. This matters because a similar web application may eventually interface with telescope hardware. Django already provides user authentication, groups, and permissions, so roles could be added by assigning users to groups and checking the group on the waveform submission view.

  Retry and resume status on the UI would show an observer when a failed transfer is being retried or resumed, instead of appearing stalled. The history page already shows a failure reason for failed transfers. A retry or resume event that includes the attempt number could be published to Kafka and displayed the same way.
