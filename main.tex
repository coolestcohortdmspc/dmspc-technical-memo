\section*{Abstract}

This software documents a real-time data transport architecture developed by the NRAO, and demonstrates a possible use for the future ngRadar system. While ngRadar was selected as a test case, the ultimate goal is to have a real-time data transport system that can be implemented into any NRAO system. The broader scope of this prototype should be kept in mind, even while this memo uses the context of the ngRadar system. The purpose of this prototype is to explore feasible design options, which will provide a proof of concept for what works and what is possible when this system gets implemented into production. Some requirements for the design options that were adhered to include public-network movement of real-time metadata and data products, closed-loop feedback, remote observing and monitoring, integration of all observing sites involved, and system health maintenance interface(s). The final software architecture is the result of experimenting with the best options for observation data transport efficiency, web application efficiency, message reliability, retention, and storage, scalability, and more.

\section{Introduction} \label{Introduction}

The ngRadar system will utilize the Green Bank Telescope (GBT), equipped with a high-powered transmitter, capable of scanning objects 10 times farther than the lunar distance. The Very Long Baseline Array (VLBA) will be used to receive the signal data, before being sent to the Domenici Science Operations Center (DSOC) for data processing. The System Communication Prototype was developed to demonstrate system communication between remote NRAO locations (in this use case, between the GBT, VLBA, and DSOC). 

All geographically dispersed NRAO systems would strongly benefit from one standardized system of real-time communication. Methods of sharing ephemerides, updating pointing information, and accessing quick-look products are currently not standardized; this information gets scattered across many platforms during an observation. This prototype aims to centralize all relevant real-time observation information and to provide it to users as efficiently as possible.

This paper documents an event-driven, web-based application for remote viewing of an active observation across geographically dispersed sites. The prototype has been tested with simulated observation data, and has demonstrated the ability to successfully meet all system requirements. This memo details design decisions and software components (Section \ref{Design and Implementation}), the software system architecture (Section \ref{System Architecture}), and other dependencies required by the System Communication Prototype (Section \ref{Dependencies}).

\section{Design and Implementation} \label{Design and Implementation}

The System Communication Prototype was developed using a collection of open-source frameworks, containerization tools, messaging infrastructures, data storage technologies, and monitoring services. These technologies support the prototype's user interface, geographically distributed simulators, event-driven communication, data transfer operations, and performance monitoring.


\subsection*{Desktop Application versus Web Application}
  To enable system communication across NRAO sites, the software needs to be compatible with various types of machines and operating systems. For use in ngRadar, the software would need to communicate across the continental United States, Hawaii, and the Caribbean.
    
  An initial investigation was completed to evaluate the viability of developing locally installed desktop applicatons, which would transmit data over the internet to software at other locations. However, this would have required compiling and building an application for all three major operating systems. Therefore, it was decided that the software would not be locally hosted, and instead function as a web application. This website would be primarily hosted on a DSOC cloud-hosted server and be accessible over the public internet, with other software components similarly hosted on a GBT cloud-hosted server and 10 VLBA simulators hosted on several VLBA cloud-hosted servers.

  Ultimately, Apache Kafka was selected as the message broker for this prototype as it has many highlights: extensive use across the industry, high reliability and customization when sending or receiving messages, and a large amount of documentation \cite{mickael_maison_getting_nodate}. One of the most important features of Kafka for this prototype is the publish/subscribe model, and the ability for multiple consumers to retrieve information from a single producer. 
  
  Kafka has numerous options for online hosting, including Confluent Cloud. An early version of the prototype was configured with a free-trial of Confluent Cloud, but a self-hosted Kafka instance was later implemented due to lower cost, increased flexibility, and more control over data.


The prototype implemented a three-broker Kafka cluster using KRaft for cluster metadata management, eliminating the need for a separate Apache ZooKeeper service (as older versions of Kafka required). Kafka brokers are deployed across multiple cloud-hosted servers. Supporting containers include Kafka UI, which provides a web interface for inspecting topics and messages, and a Kafka initialization service responsible for creating the required topics during environment startup.

 \begin{itemize}
  \item Four Kafka topics are used to coordinate the simulated observation workflow:
  \begin{itemize}
    \item GBT notif: Events associated with GBT waveform selection and transmission.
    \item VLBA notif: Events associated with VLBA station processing, storage requests, and data transfers.
    \item DSOC notif: Events associated with DSOC processing, storage responses, DDM image processing and storage, and observation completion.
    \item progress tracking: Progress updates associated with ExpeDat data streaming.
  \end{itemize}
\end{itemize}

The GBT, VLBA, and DSOC simulators communicate by publishing and consuming Kafka messages consisting of event notifications and workflow metadata. For example, submitting a waveform through the Django website publishes an event to GBT notif, which is consumed by the GBT simulator. Subsequent messages coordinate the simulated transmission, VLBA processing, storage negotiation, data transfer, and DSOC processing stages.

Kafka messages use a common payload structure containing observation identifiers, station information, waveform metadata, processing status, timestamps, and other fields relevant to the simulation. As an observation progresses, producers populate additional metadata required by downstream consumers. Kafka message keys identify event types so consumers can distinguish actionable workflow messages from other notifications.

Two additional consumers support the website and database. The UI consumer subscribes to the simulation topics and forwards relevant events to the frontend using SSE (server-sent events), enabling the website homepage to function independently from the database during a simulated observation. The database consumer also subscribes to the simulation topics, with the added responsibility of pesisting these simulated events in a PostgreSQL database and then forwards those events to the frontend using SSE to update the Events History Page. Both the UI consumer and database consumer operate independently of the GBT, DSOC, and 10 VLBA simulators.

  
\subsection*{Docker}

In this prototype, Docker containers were used to ensure that the software could be run across multiple machines for local development, and perform reliably when run on a server. Each of the major software components has its own container, which made development of the software more flexible, as the code for each service could be changed without altering another container. It also made it easier to replace individual services in the code with alternatives if changes were necessary. Use of containers also improved fault tolerance for the website - during testing, there were several times that a container had stopped working. This did cause some features to stop working correctly, but did not cause the website to crash as a whole.

Containerization ensures that any computer which has the Docker Engine - a server responsible for managing the containers - can run this web application with consistent performance.

All major components of the prototype were containerized using Docker, including the GBT simulator, 10 VLBA station simulators, DSOC simulator, Django website, a three-node Kafka cluster, PostgreSQL database, SeaweedFS object storage, as well as performance monitoring tools. The complete development and deployment environment consists of approximately 34 containers, depending on the enabled services.

Docker Compose is used to define the containerized environment through YAML configuration files. These configurations specify container images, build instructions, environment variables, startup commands, port mappings, volumes, and networking settings. Docker Compose also allows for starting, stopping, and rebuilding services during development and deployment. For ease of use, a control script is utilized and kept up to date with common Docker invocations.

Containers running on the same Docker host communicate through a Docker-managed bridge network. Docker's internal DNS service allows containers to reference one another using service names rather than fixed IP addresses. Communication between containers deployed on remote servers use network-accessible host endpoints, protected by a cloud firewall.

Docker volumes and bind mounts are used to persist application data and share directories between containers when necessary. For example, shared directories support simulated observation data streaming, while persistent volumes are used for services such as PostgreSQL and SeaweedFS.

\subsection*{PostgreSQL Database}
The prototype uses PostgreSQL as its database for application data and historical simulated events. The database runs in a Docker container and is accessed by the Django application through Django's Object-Relational Mapper (ORM).

Django models define the database structures used to represent observations, simulation events, station identifiers, processing statuses, and associated metadata. The database consumer subscribes to the GBT, DSOC, and VLBA Kafka topics and persists simulated events to PostgreSQL as an observation progresses. These records include observation identifiers, event timestamps, station names, waveform selections, processing statuses, data streaming metadata, and latency measurements.

The Django website uses PostgreSQL to populate the Events History Page. When the history page initially loads, Django queries the database once to retrieve previously recorded events. During an active observation, the database consumer persists incoming Kafka events to PostgreSQL before publishing real-time updates through Server-Sent Events (SSE), allowing the history page to display newly recorded events without database polling or manual page refreshes.

Both the database consumer and the UI consumer utilize the same SSE broker and shared browser connection to deliver updates to their respective web pages. However, their data handling differs: the homepage is completely decoupled from PostgreSQL and receives live simulated updates directly from Kafka through the UI consumer, while the history page relies on PostgreSQL for initial data retrieval and requires events to be recorded by the database consumer and saved in the database before corresponding SSE updates are delivered.

After a data streaming process completes, the DSOC simulator verifies that the received data size matches the expected data size before continuing its processing workflow. Kafka handles the control messages coordinating these operations, while ExpeDat handles the actual data streaming.

\subsection*{Performance \& Monitoring Tools}
The prototype incorporates several monitoring and performance testing technologies to observe container health, collect application and infrastructure metrics, measure website performance, and trace processing operations across the distributed system.

\subsubsection*{Traefik Reverse Proxy}
Traefik is an open-source reverse proxy and load balancer that routes incoming HTTP and HTTPS requests to backend services \cite{traefik_labs_traefik_nodate}. It supports Docker integration, allowing routing configurations to reference containerized services. The prototype uses Traefik to expose the Django website to the public internet. Traefik runs in a Docker container on the DSOC Droplet and forwards incoming website requests to the Django web application running on the internal Docker network. Traefik provides HTTPS termination and supports automated TLS certificate management through Let's Encrypt. Traefik also exposes Prometheus-compatible metrics, allowing request traffic and reverse-proxy performance to be monitored through the prototype's observability infrastructure.

\subsubsection*{Portainer Container Management}
Portainer allows users to inspect running containers, view logs, monitor resource utilization, and manage container lifecycle operations. The prototype uses a centralized Portainer instance hosted on the DSOC Droplet, with Portainer agents deployed on the other geographically distributed Droplets. The agents provide remote access through the central Portainer instance. This configuration provides the ability to inspect container statuses, restart services, review logs, and monitor Docker resources across the deployment without having to deploy multiple Portainer instances.

\subsubsection*{Grafana}
The following tools are all open-source projects created and maintained by Grafana Labs, enabling a comprehensive monitoring suite that is highly customizable \cite{grafana_labs_technical_nodate}. 

Prometheus is a monitoring system that collects and stores numerical time-series metrics. It periodically retrieves metrics from configured HTTP endpoints, commonly referred to as scrape targets, and stores them for querying and visualization. The prototype uses Prometheus to collect application, container, and infrastructure performance metrics. Exporters expose measurements from supporting technologies, including Kafka and PostgreSQL, in a format that Prometheus can scrape. The monitoring environment includes exporters for collecting information such as Kafka consumer lag, broker and topic statistics, database activity, and system resource utilization. Additional metrics from instrumented application components and Traefik provide visibility into application and HTTP request behavior. Prometheus serves as a metrics data source for Grafana, where the collected measurements are displayed in monitoring dashboards.

k6 is a performance testing tool used to generate HTTP traffic and measure application behavior under simulated workloads. Tests are defined using JavaScript and can be configured with virtual users, iterations, execution durations, and performance thresholds. The prototype uses k6 to perform load testing against the Django web application. Test scripts simulate user interactions with the website, including authenticated requests, observation submission operations, and requests to application endpoints. The tests collect measurements such as HTTP request duration, request failure rate, response times, and successful request checks. Configurable thresholds allow for evaluating application behavior against defined performance targets. These measurements are used to establish a performance baseline for the website and identify potential bottlenecks as the number of concurrent requests or simulated users increases.

OpenTelemetry is an observability framework that provides APIs, SDKs, and instrumentation tools for collecting telemetry data from applications. It supports distributed tracing, metrics, and logs. The prototype uses OpenTelemetry to instrument Python application components, including the GBT, VLBA, and DSOC simulators and Kafka-consuming processes. Instrumented operations generate trace spans containing information such as operation names, timestamps, execution durations, Kafka topics, message offsets, and processing statuses. Trace context is propagated through Kafka message headers so that processing operations across different containers can be associated with the same distributed trace. This allows individual workflow operations to be examined across producer and consumer boundaries. An OpenTelemetry Collector runs as a Docker service and receives telemetry exported by instrumented components using the OpenTelemetry Protocol (OTLP). The collector processes the incoming telemetry and forwards trace data to Grafana Tempo. Tempo is a distributed tracing backend that stores and retrieves traces. It is integrated with Grafana, and provides the ability to inspect individual spans, trace execution paths, identify failed operations, and analyze processing durations across the simulated observation workflow.

Grafana is a visualization and observability platform used to build dashboards from metrics, logs, and tracing data sources. Two data sources were integrated for the prototype's data visualization needs in Grafana: Prometheus for time-series metrics and Tempo for distributed tracing. Grafana is used as an interface for viewing system performance and observability data. A centralized Grafana dashboard was created to display metrics collected by Prometheus, including infrastructure resource utilization, Kafka activity, HTTP request performance, application measurements, and OpenTelemetry metrics stored by Tempo. The custom Grafana dashboard organizes these metrics by component into different tabs, providing a centralized view of the prototype's operational behavior and supporting performance analysis for development and testing.

Figure \ref{fig:container} shows the container-level view of the prototype. Users reach the public website, exposed by a reverse proxy, to view the latest updates regarding an observation and request different waveforms to be transmitted by the GBT. Apache Kafka is the high-throughput mesage broker used in the system, storing and transporting messages that trigger workflow items. A 3-node Kafka cluster was implemented for this prototype to enable redundancy and protection against data loss (full Kafka functionality detailed in Section \ref{Design and Implementation}). The web application container is capable of sending to and receiving messages from the broker to trigger workflow events and receive updates. The database consumer container can also receive messages from the broker and is responsible for saving records to the database and populating the history table on the UI.

\centering 
\includegraphics[width=0.85\columnwidth]{figures/containerdiagram.png} 
    \caption{Container diagram showing system structure.} 
    \label{fig:container}
\end{figure}

The NRAO site simulators (GBT, VLBA, and DSOC) are Python programs that perform site-specific logic. They receive messages from the broker that trigger certain events, depending on the key of the message.  


Figure \ref{fig:sequence} shows the sequence of events that occurs after a user submits a waveform. The final prototype is to scale, meaning there are 10 VLBA site simulators. Each VLBA site receives the Kafka message published by the GBT so they can each connect with DSOC and stream raw data. The DSOC simulator is comprised of 3 main components, or microservices, that share a Docker volume. ExpeDat file streaming is used within the VLBA simulators to transfer data to the DSOC ExpeDat server only after DSOC confirms that it has room to accept incoming data. The Central Processing Site is responsible for those storage checks and generating quick-look products (DDMs in this prototype). After DSOC saves the quick-look product to object storage, the VLBA is notified that it can delete itWs raw data. 

Every Kafka message from Step 1 through Step 9 persists the same UUID and observation metadata so everything related to the waveform request from the user is relational. Because there are 10 VLBA stations, every Kafka message also has a second UUID that persists which station recorded what data. So, the sequence diagram remains identical regardless of the number of active VLBA stations.

\centering 
\includegraphics[width=0.85\columnwidth]{figures/sequencediagram.png} 
    \caption{Sequence diagram depicting the triggered events throughout the system.} 
    \label{fig:sequence}
\end{figure}

Not shown in Figure \ref{fig:sequence}, but worth noting, is the other type of Kafka messages that the Progress Tracker service at the DSOC simulator is publishing. It reports the status of each VLBA station's streaming progress to the message broker, which a consumer in the Django application is reading. A progress bar for each VLBA station is then shown on the homepage to keep users informed on when they can expect quick-look products to arrive.

\section{Dependencies} \label{Dependencies}

  This section describes the dependencies required for the System Communication Prototype to function properly. These dependencies include software libraries, external services, and hardware requirements. The versions are a snapshot as of October 2026. Sources are \texttt{requirements.txt}, \texttt{Dockerfile}, \texttt{docker-compose.yml}, and the running containers. The only proprietary or licensed dependency is ExpeDat. Some versions are not fixed in those files, so a rebuild may install different versions than the ones listed here.

\subsection*{Language and Runtime}

  The chosen language is Python because the prototype involves a large amount of data transfer and management. Python is also widely used across astronomy, all prototyping team members have prior experience with it, and the website does not require the extra computing speed offered by compiled languages such as C++. All components are containerized in Docker to simplify compatibility. The version is Python 3.11 (the \texttt{python:3.11-slim} base image, running 3.11.15).

\subsection*{Web Framework and ASGI}

  ASGI is the modern standard for Python web applications that support asynchronous communication, while WSGI is the classic standard for synchronous communication. ASGI supports async views and server-sent events (SSE). SSEs push updates to the browser as they happen, replacing the database polling used early in development, which became a performance bottleneck. Uvicorn is used to run the ASGI application. Django is constrained to run versions from 5.2 through 5.3.

\subsection*{Kafka}

  There are three brokers in KRaft mode, so that if one is down, the others can stay up. The JMX exporter is used as a Java agent to expose broker metrics to Prometheus, so that they can be shown on the Grafana dashboard. The one-shot \texttt{kafka-init} container, built on the cp-kafka image, creates the topics. The Python client is confluent-kafka, built on librdkafka.

\subsection*{Database and Object Store}

  PostgreSQL is used for the database, with psycopg, psycopg-binary, and postgres-exporter. SeaweedFS is used as an object storage for storing simulated DDM images, with Boto3 and Botocore to communicate with the S3 gateway. To generate these simulated DDM images, numpy, pandas, matplotlib and pillow are used.

\subsection*{Data Movement}

  The prototype experiments with two data transfer tools: etransfer and ExpeDat. Etransfer (v2.0, from JIVE) is free and open source, so it is compiled from source at build time. It needs a C++11 compiler, bundles its own UDT and SRT libraries, and listens on port 4004 for commands (TCP) and port 8008 for data (SRT). ExpeDat (\texttt{servedat} 1.23.1, MTP 4.5.3) is proprietary: the vendor ships ready-made binaries, which are copied into the image at build time, with separate arm64 and x86-64 builds. The extended free trial is valid for 21 days, so production use would need a license.

\subsection*{Testing and Load Testing}

  Pytest, pytest-django, pytest-cov and pytest-asyncio are used for unit testing logical components of backend processes, and k6 is used for system performance testing and runs in its own container.

\subsection*{Infrastructure and Monitoring}

  Traefik is used to handle HTTPS and UDP routes. Docker Desktop is used to interface with containerized services during local development. Portainer, Prometheus and Grafana use latest-tag images.

\subsection*{Hardware and Hosting}

  The project is deployed on DigitalOcean. There are four Droplets with 1 vCPU, 2 GB RAM and 50 GB disk for GBT and VLBA, and one Droplet with 4 vCPU, 8 GB RAM and 160 GB disk for DSOC, where the database, image storage, ExpeDat server and other containers are hosted. Note that development is on arm64 (Apple Silicon) while the Droplets are x86-64, so the binaries must match.

\section{Ideas for Future Improvements} \label{Future}


  The prototype demonstrates the full event flow, and the items below are what remain for a production-ready ngRadar system. The section is organized as known issues, improvements, and features.

\subsection*{Known Issues}

  The submit new waveform button unlocks after the first of several concurrent VLBA transfers completes, rather than after all of them have completed. A new waveform can therefore be submitted while earlier transfers are still running. The button should stay locked until every transfer in the sequence is complete.

  Part way through the prototype's development, a large refactor decoupled the UI from the PostgreSQL database and made the UI completely event-driven, relying on Kafka for updates instead of polling the database. Before this refactor, certain safeguards ensured that the website, backend processes, and Docker ecosystem could fail gracefully and print helpful logs for debugging and restarting, rather than failing and exiting. Not all of graceful failure scenarios have been tested since the UI bridge refactor. Going back through those scenarios completely would confirm that the prototype still fails gracefully.

  The \texttt{vlba\_sim} container stops reading Kafka for up to 15 minutes while it waits for the daemon after an outage. A waveform submitted during this time sits unprocessed until the wait resolves. Reading Kafka messages while waiting would remove this delay.

  Etransfer's \texttt{-6} return code cannot separate a stopped daemon from network loss, so the error message cannot name the cause. The message describes what the code means (a connection or write failure), not a guaranteed root cause.

\subsection*{Improvements}

  Moving from cloud hosting to in-house infrastructure is worth evaluating. The main reason is full control over the sequence of events, with the ability to configure the servers, network, and services however the project requires. The cloud Droplets also limit the available CPU, RAM, and storage. The trade-offs are cost, maintenance, reachability from VLBA sites, and security.

  Kafka runs out of memory on the 2 GB Droplets. Each node uses about 800 MB of RAM, and with no swap configured, the Linux out-of-memory killer stopped two of the three Kafka nodes. The fixes are more RAM or a swap file, and restart policies on the Kafka containers.

  The capacity of the data transfer path is not yet characterized. Concurrent overlap of transfers was never measured, and no real-network bandwidth or latency numbers exist. During testing, a limit on the number of concurrent transfers was suspected, but there is no direct proof of one. If such a limit exists, it could come from the resources retained on the Droplet rather than from ExpeDat itself. Measuring CPU, RAM, and disk usage with the existing Prometheus and Grafana dashboards while increasing the number of simultaneous transfers would show which.

\subsection*{Features}

  Originally, DSOC checked its storage and responded to a single VLBA station about whether it could accept the incoming etransfer or ExpeDat raw data transfer/stream. Currently, this check occurs simultaneously for all 10 VLBA stations. With 10 consecutive storage check requests, DSOC responds yes without accounting for the requests it has already approved, so with simultaneous transfers or streams, DSOC storage could exceed its limit for incoming raw data. DSOC should keep a running storage count, updated before and after each approval of a VLBA site's incoming transfer or stream.

  On the history events page, DSOC sends a ``Completed'' Kafka message 10 times for the 10 VLBA simulators. DSOC should instead wait until all 10 VLBA raw data transfers are processed and the 10 DDM images are generated and stored in SeaweedFS, and then send a single ``Completed'' message. This message is displayed on the UI and tells the remote observer that the sequence of events has finished.

  Observer notifications would alert a remote observer when a sequence completes or fails, so the history page does not need to be watched continuously. Because every event already passes through Kafka, a new consumer could subscribe to the existing topics and send an email or chat message when it sees a completion or failure event. Grafana also supports alerting directly on the metrics it already aggregates from Prometheus, which could notify observers without a separate Kafka consumer; this prototype did not explore Grafana's built-in alerting and logging features. 

  User roles would separate what observers and operators are allowed to do. For example, observers could view the home and history pages, while only operators could submit a new waveform. This matters because a similar web application may eventually interface with telescope hardware. Django already provides user authentication, groups, and permissions, so roles could be added by assigning users to groups and checking the group on the waveform submission view.

  Retry and resume status on the UI would show an observer when a failed transfer is being retried or resumed, instead of appearing stalled. The history page already shows a failure reason for failed transfers. A retry or resume event that includes the attempt number could be published to Kafka and displayed the same way.
