\section*{Abstract}

\textbf{Ultimate goal of why we built this prototype: to explore feasible design options for ngRadar inter-site data communication, so that the project can make informed architectural decisions about public-network data movement, remote observing, and real-time feedback between GBO, VLBA sites, DSOC, and observers or operators. Also to create a system that could be used in other areas of the observatory, outside just the context of ngRadar}

Interferometers used in Radio Astronomy require real time communication between antenna sites and new instruments, such as the ngVLA, and ngRadar would strongly benefit from system communication between observation planning, telescope control, and data transport software. Currently, there is no direct connection between these software components and NRAO personel must communicate directly to plan observations across sites.
This software documents a real-time data transport architecture developed by the NRAO, and demonstrates a possible use in the future ngRadar system, but could be implemented into any radio astronomy observatory. The software architecture is entirely event-driven while each event is also saved in a central database, with every event visible to users on a public website. The prototype has been tested with simulated observation data, and has demonstrated the ability to work remotely across geographically dispersed sites.

\section{Design Decisions} \label{Design Decisions}

\subsection*{Desktop Application versus Web Application}
  To enable system communication across NRAO sites, the software needs to be compatible with various types of machines and operating systems. For use in ngRadar, the software would need to communicate across the continental United States, Hawaii, and the Caribbean.
    
  The team initially investigated developing software which would be installed locally on the computers of NRAO employees, and transmit data over the internet to the software at other locations. However, this would have required compiling and building an application for all three major operating systems. Therefore, it was decided that the software would not be locally hosted, and instead function as a web application. This website would be primarily hosted on servers at DSOC, with other software components hosted at the Green Bank Observatory and on all 10 of the VLBA sites. 

\subsection*{Backend Frameworks}

There were three frameworks our team investigated - Flask, FastAPI, and Django.
  Flask is well-known for its simplicity and low usage of computing resources. It is also flexible and modular, allowing developers to modify the framework and integrate additional software components for added functionality. However, Flask only supports using synchronous communication between the server and framework, meaning processes can only run one-at-a-time. Flask also does not have built in authentication or adminstrative features.

  FastAPI provides high-speed, and asynchronous, non-blocking communication in a relatively lightweight framework. It is the newest framework we investigated and includes features such as built in authentication, python code completion to speed up development, and automatic documentation for program APIs. It includes a modest number of built in functionality, and developers can add libraries with additional features they need.

  Django is a framework with a large amount of built in functionality including an adminstrative dashboard, user authentication, HTML form processing, and an object-relational mapper for database interaction [\textbf{Revisit and add any additional built-in features we used}]. It is capable of running large web applications with many users. By default, Django runs with synchronous communication, but libraries that add asynchronous communication are avaliable.

  After considering all three frameworks, Django was chosen due to the large number of compatible software libraries, built in security and adminstrative features, and its ability to scale as website traffic grows.


\subsection*{Message Brokers}

  Real time data transmission across geographically separated locations was a defining requirement of our software prototype, and choosing a software tool to accomplish this was a major decision the team needed to make early in the design process. Initially, the team was considering using Socket programming for communication over the internet, but the added complexity of developing our own code to do this reliably with multiple computers led us to investigate using an existing message broker to accomplish this.

There were three message brokers the team investigated using - Apache Kafka, RabbitMQ, and Apache Pulsar. Apache Kafka was first released to the public in 2011, and is the most widely used message broker across the industry. It is best suited for high volume data transmission, and uses a central server known as a cluster, with one or more message brokers to handle requests from producers and consumers. Kafka uses "producers" to send messages to user-defined topics. Messages are stored in these topics in subgroups called partitions, either until consumption is confirmed or for a fixed number of days. "Consumers" are used to receive messages from these topics. The initial time to implement a basic Kafka messaging setup was minimal; however, scaling up the system and debugging errors adds significant complexity. Kafka can also use more computing resources than necessary if only sending a small amount of data. However, Kafka is very reliable, and has several built in methods to prevent data loss if servers crash. 

RabbitMQ was also considered as a broker option; it has the lowest message latency and lowest server memory requirement compared to the other two options, and is a significantly simpler system. This option was not chosen due to RabbitMQ's push model (producer controls the flow of messages and can overwhelm consumers) and the difficulty in scaling up the system. Apache Pulsar, the third option considered, is the newest of the three message brokers and attempts to combine the features of Kafka and RabbitMQ. Pulsar is well suited for scaling up to handle high volumes of data. However, with the extra features Pulsar offers, it is more complex to setup than Kafka, has a higher message latency due to the extra storage layers, and has less documentation avaliable.

  Ultimately the team decided to select Kafka, as it has many highlights: extensive use across the industry, high reliability and customization when sending or receiving messages, and the large amount of documentation avaliable for it. One of the most important features of Kafka for our prototype is the publish/subscribe model, and the ability for multiple consumers to retrieve information from a single producer. 
  
  Kafka has numerous options for online broker hosting, and initially the website was set up to work with Confluent Cloud. However, the team chose locally hosted Kafka brokers due to lower cost, increased flexibility, and more control over the data on those brokers.

\subsection*{SQL Database}

\subsection*{Object Store}

  This software prototype simulates generating DDM images from the VLBA Antenna stations, and storing these images directly in a database as binary files significantly reduces performance and increases database size when large numbers of images need to be produced. Using a dedicated Object Store means the database only needs to store text-based information, enabling faster database queries and the ability to serve images using SDKs such as Amazon Boto3. 

    There were three object stores the team investigated: MinIO, Garage, and SeaweedFS. MinIO was first released in 2015 as an open source object store, with features including an administration panel, data encryption and authentication, support for object version control, forward error correction, and is optimized for parallel request handling. However, in late 2025, MinIO shifted to focus on commerical customers, and no longer maintains the open source code. It can still be downloaded from GitHub, although some of its features have been removed, and users must build it from source now. Garage is the second object store we investigated, and it is designed to be simple and use minimal computer resources. It offers a modest feature set, including data compression and backup, Amazon Boto3 integration, and an online admin interface. However, to install and set up the software, it must be built directly from the source code, which would add time and complexity to the project. The last object store the team researched was SeaweedFS, a distributed storage system designed to handle large numbers of files and scale with linear efficiency. Some additional features include data protection, file recovery, efficient metadata management, flexible deployment, and compatibility with multiple storage volumes, including Boto3. The SeaweedFS code comes packaged as a binary file with a built-in installer and a setup guide for Docker, making installation easy. After installation, there are three major software components of SeaweedFS: the Master server, Volume servers, and the Filer Server, which provides file system semantics. 

    The team chose to implement SeaweedFS as the object store for our website because it is fully open source and actively maintained, it is easy to set up across multiple operating systems, performs well when used with large numbers of files, includes data protection features, and guides on how to set up a Docker container for it.

  

\subsection*{Data Movement}

  Etransfer is the first data transfer tool tested within this prototype, which was developed by the Joint Institute for VLBI ERIC (JIVE) and has become the standard data transfer tool within the VLBI community. The code repository for this tool is free to use and open source, which benefits development by allowing us to adjust the code as needed \cite{marjolein_verkouter_jive-vlbietransfer_2026}. Etransfer supports TCP, UDT, and SRT, with UDT and SRT being the recommended protocols. The etransfer client (etc) and etransfer daemon (etd) system allows the client program to initiate both client to server transfer, as well as server to server transfers, during which the data does not flow through the client's machine and/or network (note that server and daemon are interchangeable). This tool supports resuming failed transfers, mutliple transfers to one daemon in parallel, and Access Control Lists to define allowed/denied directories. It does not yet support authentication and authorization.


  ExpeDat is the second data transfer tool the team evaluated for use in this website, and it was developed by Data Expedition Incorporated. Unlike most of the other code in this prototype, it is proprietary and uses the Multipurpose Transcation Protocol (MTP), a data transport protocol which can adapt to changes in network conditions, and is based on the open source User Datagram Protocol (UDP). The software consists of a server and several client applications to move files between networked computers. It is capable of resuming incomplete file transfers, compressing data before transferring it, tracking file upload status, and remotely monitoring the server status. These settings can be changed in the \textit{servedat.cf} and \textit{svpasswd} files. The client and server can be set up and installed on Windows, Linux, and MacOS, or configured to run inside a docker container.


\subsection*{Cloud-Hosting Solutions}

  While developing this website, the team needed a way to test our simulated data from geographically distributed locations. If this software architecture was implemented to work with telescope hardware, it would be hosted using servers on site at NRAO locations across the county. The website could then be used to communicate between observatory sites, and inform remote viewers of real-time events during an active observation.

  There were two platforms the chose to host the website on during this process, the first was Render and the second was Digital Ocean. Render offers a free option for hosting small websites with very limited performance - 1GB of storage, 256 MB of RAM, and 1/10th of a virtual CPU. This offered a way for the team to demonstrate the website to other observatory personel over the public internet, but performance was very slow. Render offers paid subscriptions starting at $7, but the least expensive plan which includes 1 virtual CPU is $25 per month, and includes only 2GB of RAM. The limited performance and expensive cost of using Render led the team to stop using it and explore alternatives.
  
  DigitalOcean is a cloud hosting platform, which sells access to Virtual Machines, known as "Droplets" at various locations worldwide. After testing the performance of a single Droplet, the team set up Droplets on servers located in New York, San Francisco, London, Bangalore, and Sydney to run our website containers. Digital Ocean offers Droplets with varying performance levels, and our team purchased monthly subscriptions to four entry level droplets, and one mid-tier droplet. Each entry level Droplet offered 1 virtual CPU (vCPU), 2GB of RAM, 50GB of storage, and costs \$12 per month. The mid tier droplet has 4 vCPUs, 8GB of RAM, 160GB of storage, and costs \$48 per month. The portion of our website representing DSOC contains the software tools which managed the SQL database, Kafka brokers, E-transfer (or ExpeDat) server, SeaweedFS file store, and various performance monitoring tools. To perform at an acceptable speed and support multiple website users, the team found that DSOC needed to use this mid-tier droplet. The other portions of our website, including the GBT and VLBA simulators, were spread out evenly across the 5 Droplets. Since migrating the website to work on Digital Ocean, performance has significantly improved, even when many people  are using it at once. Currently, this prototype website costs \$96 per month to operate on a cloud hosted service, but that cost will only exist during the development phase.

\section{Software Stack} \label{Software Stack}
The System Communication Prototype was developed using a collection of open-source frameworks, containerization tools, messaging infrastructures, data storage technologies, and monitoring services. These technologies support the prototype's web interface, geographically distributed simulators, event-driven communication, data transfer operations, and performance monitoring.

\subsection*{Django-Based Web Application}
The ngRadar web application was developed using Python and Django, a high-level web framework that provides built-in functionality for URL routing, database integration, user authentication, and server-side HTML rendering. Django follows a Model-View-Template (MVT) architecture, in which models define the application's data structures, views handle incoming HTTP requests and application logic, and templates generate the HTML presented to users. The frontend was implemented using HTML, CSS, JavaScript, and Bootstrap, without introducing a separate frontend framework. Django templates render the application's pages, while JavaScript manages user interactions and dynamically updates the interface. Bootstrap provides reusable styling components and responsive page layouts.

The Django application runs using the Asynchronous Server Gateway Interface (ASGI), which supports asynchronous connections and long-lived HTTP responses. The prototype web application requires two Kafka consumers for updating the user interface via Server-Sent Events (SSE) to deliver real-time simulation updates from the backend to connected browsers. One Kafka consumer (UI consumer) runs within the website container, listens for simulation events, and forwards relevant updates to the homepage through SSE. A second Kafka consumer (database consumer) listens for the same events, but also persists a historical record of all events before first forwarding relevant updates to the history events page. This means that the homepage is fully decoupled from the database during an active simulated observation as Kafka event messages are forwarded directly to the homepage, and the history events page, while still coupled to the database, does not require constant database polling for new updates to the website. 


\subsection*{Docker Containerization}
All major components of the System Communication Prototype were containerized using Docker, including the GBT simulator, ten VLBA station simulators, DSOC simulator, Django website, Kafka infrastructure, PostgreSQL database, SeaweedFS storage services, and monitoring tools. The complete development and deployment environment consisted of approximately 34 containers, depending on the enabled services.

Docker Compose was used to define and manage the containerized environment through YAML configuration files. These configurations specify container images, build instructions, environment variables, startup commands, port mappings, volumes, and networking settings. Docker Compose also allowed the team to start, stop, rebuild, and recreate groups of related services during development and deployment. For ease of use, the team utilized a control script kept up to date with commands for common Docker invocations.

Containers running on the same Docker host communicated through Docker-managed bridge networks. Docker's internal DNS service allowed containers to reference one another using service names rather than fixed IP addresses. Communication between containers deployed on separate DigitalOcean Droplets used network-accessible host endpoints, protected by DigitalOcean's cloud firewall.

Docker volumes and bind mounts were used to persist application data and share directories between containers when necessary. For example, shared directories supported simulated observation data streaming, while persistent volumes were used for services such as PostgreSQL and SeaweedFS.

\subsection*{Apache Kafka Event Messenger}
Apache Kafka is a distributed event-streaming platform used to publish, store, and consume event messages between independent application components. Kafka organizes messages into topics, allowing producers to publish events and consumers to subscribe to the topics relevant to their processing responsibilities.

The prototype implemented a three-broker Kafka cluster using KRaft for cluster metadata management, eliminating the need for a separate Apache ZooKeeper service. Kafka brokers were deployed across multiple DigitalOcean Droplets. Supporting containers included Kafka UI, which provides a web interface for inspecting topics and messages, and a Kafka initialization service responsible for creating the required topics during environment startup.

 \begin{itemize}
  \item Four Kafka topics were used to coordinate the simulated observation workflow:
  \begin{itemize}
    \item GBT notif: Events associated with GBT waveform selection and transmission.
    \item VLBA notif: Events associated with VLBA station processing, storage requests, and data transfers.
    \item DSOC notif: Events associated with DSOC processing, storage responses, and observation completion.
    \item progress tracking: Progress updates associated with ExpeDat data streaming.
  \end{itemize}
\end{itemize}

The GBT, VLBA, and DSOC simulators communicate by publishing and consuming Kafka messages. For example, submitting a waveform through the Django website publishes an event to GBT notif, which is consumed by the GBT simulator. Subsequent messages coordinate the simulated transmission, VLBA processing, storage negotiation, data transfer, and DSOC processing stages.

Kafka messages use a common payload structure containing observation identifiers, station information, waveform metadata, processing status, timestamps, and other fields relevant to the simulation. As an observation progresses, producers populate additional metadata required by downstream consumers. Kafka message keys identify event types so consumers can distinguish actionable workflow messages from other notifications.

Two additional consumers support the website and database. The UI consumer subscribes to the simulation topics and forwards relevant events to the frontend using SSE, while the database consumer records simulation events in PostgreSQL for historical persistence. Both consumers operate independently of the observatory simulators.

Kafka is used to transmit event notifications and workflow metadata rather than large observation data files. The simulated scientific data is streamed separately using ExpeDat.


\subsection*{PostgreSQL Database}
The prototype uses PostgreSQL as its primary persistent database for application data and historical simulation events. The database runs in a Docker container and is accessed by the Django application through Django's Object-Relational Mapper (ORM).

Django models define the database structures used to represent observations, simulation events, station identifiers, processing statuses, and associated metadata. A dedicated database consumer subscribes to all four Kafka topics and persists simulation events to PostgreSQL as an observation progresses. These records include observation identifiers, event timestamps, station names, waveform selections, processing statuses, data streaming metadata, and latency measurements.

The Django website uses PostgreSQL to populate its historical observation interface. When the history page initially loads, Django queries the database to retrieve previously recorded events. During an active observation, the database consumer persists incoming Kafka events to PostgreSQL before publishing real-time updates through Server-Sent Events (SSE), allowing the history page to display newly recorded events without additional database polling or manual page refreshes.

Both the database consumer and the UI consumer utilize the same SSE broker and shared browser connection to deliver updates to their respective interfaces. However, their data handling differs: the homepage is completely decoupled from PostgreSQL and receives live simulation updates directly from Kafka through the UI consumer, while the history page relies on PostgreSQL for initial data retrieval and requires events to be persisted by the database consumer before corresponding SSE updates are delivered. This ensures that events displayed in the history interface have already been recorded in the database.


\subsection*{ExpeDat Data Streaming}
ExpeDat is a high-performance technology designed to deliver data efficiently across networks, including wide-area connections with significant latency. ExpeDat supports both file transfer and streaming capabilities with the only difference being the flag used in the CLI command. It provides an alternative to conventional file transfer or streaming mechanisms for applications that require high-throughput movement of large datasets.

The prototype used ExpeDat's data streaming feature to simulate streaming raw observation data from the VLBA station containers to the DSOC environment. Each VLBA simulator initiates a data streaming process after receiving the appropriate workflow notifications and confirmation that the DSOC environment has sufficient storage capacity.

The streaming process uses ExpeDat client and server components to send simulated observation data to a destination directory accessible to the DSOC simulator. This streaming progress is monitored and published to Kafka through the progress tracking topic, allowing the Django website to display progress updates for the remote observer regarding the individual VLBA stations' streaming progress.

After a data streaming process completes, the DSOC simulator verifies that the received data matches the expected data size before continuing its processing workflow. Kafka handles the control messages coordinating these operations, while ExpeDat handles the actual data streaming.


\subsection*{SeaweedFS - Object Store}
SeaweedFS is an open-source distributed storage system that supports file storage and object storage through an Amazon S3-compatible interface. Its S3 API allows applications to store and retrieve objects using standard object-storage operations.

The prototype uses SeaweedFS as an object store for the simulated Delay-Doppler Map (DDM) images generated by the DSOC simulator. SeaweedFS runs in the Docker environment and exposes an S3-compatible endpoint for application access.

After the DSOC simulator validates an incoming observation data stream, it generates a simulated DDM image and uploads the image to SeaweedFS. The resulting object key is included in the observation metadata and persisted in PostgreSQL, allowing the Django application to locate and display the generated image for that associated simulated observation event. SeaweedFS is used specifically for storing generated image products, while PostgreSQL maintains the associated structured observation metadata.

\subsection*{DigitalOcean Droplets}
DigitalOcean Droplets are Linux-based virtual machines hosted on DigitalOcean's cloud infrastructure. Each Droplet provides an independent computing environment with configurable CPU, memory, storage, and networking resources. The prototype was deployed across five DigitalOcean Droplets located in San Francisco, New York, London, Bangalore, and Sydney. Each Droplet hosted a subset of the Docker containers, distributing the simulated observatory processes across geographically separated cloud environments.

 \begin{itemize}
  \item The DigitalOcean cloud-hosted container distribution was set up as follows:
  \begin{itemize}
    
    \item San Francisco: GBT simulator, VLBA-BR, VLBA-MK, a Kafka broker, and a Portainer Agent.
    \item New York: DSOC simulator, VLBA-KP, VLBA-OV, the Django website and UI consumer, datbase consumer, PostgreSQL, SeaweedFS, Kafka infrastructure, ExpeDat server, Traefik, Portainer, and monitoring services.
    \item London: VLBA-SC, VLBA-HN, a Kafka broker, and a Portainer Agent.
    \item Bangalore: VLBA-NL, VLBA-FD, and a Portainer Agent.
    \item Sydney: VLBA-LA, VLBA-PT, and a Portainer Agent.

  \end{itemize}
\end{itemize}

The New York Droplet hosted the majority of the prototype's centralized services, including the public-facing website and UI consumer, database, database consumer, object storage, and observability infrastructure. The remaining Droplets primarily hosted the distributed GBT and VLBA simulation containers. Each droplet has a portainer agent which forwards container health metrics and control to main Portainer container hosted on the DSOC droplet. Portainer is a container management platform that provides a web-based interface for administering Docker environments. 

Each Droplet maintained its own Docker environment, with communication between geographically separated services occurring over network-accessible endpoints. This configuration allowed the prototype to execute its simulation processes across multiple cloud regions while using centralized application and storage services. This deployment allowed the prototype's geographically separated simulation components to remain connected through the Kafka messaging infrastructure and ExpeDat data streaming services.

\subsubsection*{Traefik Reverse Proxy}
Traefik is an open-source reverse proxy and load balancer that routes incoming HTTP and HTTPS requests to backend services. It supports Docker integration, allowing routing configurations to reference containerized services.

The prototype uses Traefik to expose the Django website to the public internet. Traefik runs in a Docker container on the New York Droplet and forwards incoming website requests to the Django application running on the internal Docker network.

Traefik provides HTTPS termination and supports automated TLS certificate management through Let's Encrypt. Its Docker integration allows routing rules to be configured using container labels and service definitions.

Traefik also exposes Prometheus-compatible metrics, allowing request traffic and reverse-proxy performance to be monitored through the prototype's observability infrastructure.


\subsection*{Performace \& Monitoring Tools}
The prototype incorporates several monitoring and performance testing technologies to observe container health, collect application and infrastructure metrics, measure website performance, and trace processing operations across the distributed system.

Portainer allows users to inspect running containers, view logs, monitor resource utilization, and manage container lifecycle operations. The prototype uses a centralized Portainer instance hosted on the New York Droplet, with Portainer Agents deployed on the geographically distributed Droplets. The agents provide remote access to their respective Docker environments through the central Portainer interface. This configuration allows the team to inspect container status, restart services, review logs, and monitor Docker resources across the distributed deployment without connecting individually to each Droplet.

Prometheus is an open-source monitoring system that collects and stores numerical time-series metrics. It periodically retrieves metrics from configured HTTP endpoints, commonly referred to as scrape targets, and stores them for querying and visualization. The prototype uses Prometheus to collect application, container, and infrastructure performance metrics. Exporters expose measurements from supporting technologies, including Kafka and PostgreSQL, in a format that Prometheus can scrape. The monitoring environment includes exporters for collecting information such as Kafka consumer lag, broker and topic statistics, database activity, and system resource utilization. Additional metrics from instrumented application components and Traefik provide visibility into application and HTTP request behavior. Prometheus serves as a metrics data source for Grafana, where the collected measurements are displayed in monitoring dashboards.

k6 is an open-source performance testing tool used to generate HTTP traffic and measure application behavior under simulated workloads. Tests are defined using JavaScript and can be configured with virtual users, iterations, execution durations, and performance thresholds. The prototype uses k6 to perform load testing against the Django web application. Test scripts simulate user interactions with the website, including authenticated requests, observation submission operations, and requests to application endpoints. The tests collect measurements such as HTTP request duration, request failure rate, response times, and successful request checks. Configurable thresholds allow the team to evaluate application behavior against defined performance targets. These measurements are used to establish a performance baseline for the website and identify potential bottlenecks as the number of concurrent requests or simulated users increases.

OpenTelemetry is an open-source observability framework that provides APIs, SDKs, and instrumentation tools for collecting telemetry data from applications. It supports distributed tracing, metrics, and logs. The prototype uses OpenTelemetry to instrument Python application components, including the GBT, VLBA, and DSOC simulators and Kafka-consuming processes. Instrumented operations generate trace spans containing information such as operation names, timestamps, execution durations, Kafka topics, message offsets, and processing statuses. Trace context is propagated through Kafka message headers so that processing operations across different containers can be associated with the same distributed trace. This allows individual workflow operations to be examined across producer and consumer boundaries. An OpenTelemetry Collector runs as a Docker service and receives telemetry exported by instrumented components using the OpenTelemetry Protocol (OTLP). The collector processes the incoming telemetry and forwards trace data to Grafana Tempo. Tempo is a distributed tracing backend that stores and retrieves traces. It is integrated with Grafana, allowing the team to inspect individual spans, trace execution paths, identify failed operations, and analyze processing durations across the simulated observation workflow.

Grafana is an open-source visualization and observability platform used to build dashboards from metrics, logs, and tracing data sources. It supports integrations with Prometheus for time-series metrics and Tempo for distributed tracing. The prototype uses Grafana as its central interface for viewing system performance and observability data. Grafana dashboards display metrics collected by Prometheus, including infrastructure resource utilization, Kafka activity, HTTP request performance, and application measurements. Grafana is also connected to Tempo, allowing distributed traces generated by OpenTelemetry instrumentation to be inspected through the same interface. Trace views provide visibility into processing operations performed by the individual simulators and Kafka consumers. Custom dashboards organize these measurements by application component, providing a centralized view of the prototype's operational behavior and supporting performance analysis during development and testing.

\section{Dependencies} \label{Dependencies}

  In this section, we will discuss the dependencies that are required for the System Communication Prototype to function properly. These dependencies include software libraries, external services, and hardware requirements. The versions are a snapshot as of October 2026. Sources: \texttt{requirements.txt}, \texttt{Dockerfile}, \texttt{docker-compose.yml}, and the running containers. The only proprietary or licensed dependency is ExpeDat. Some versions are not fixed in those files, so a rebuild may install different versions than the ones listed here.

\subsection*{Language and Runtime}

  The language we chose here is Python, since we have to deal with data transfer and management. We run everything in Docker to simplify compatibility. The version is Python 3.11 (the \texttt{python:3.11-slim} base image, running 3.11.15).

\subsection*{Web Framework and ASGI}

  ASGI is the modern standard for Python web applications that supports asynchronous programming, while WSGI is the classic standard for synchronous, blocking web applications. We need ASGI for async views and server-sent events. We use uvicorn to run the ASGI application. Django is constrained to \texttt{>=5.2,<5.3}.

\subsection*{Kafka}

  There are 3 brokers in KRaft mode, so that if one is down, the others can stay up. JMX exporter is used as a Java agent to expose broker metrics to Prometheus, so that they can be shown on the Grafana dashboard. The one-shot \texttt{kafka-init} container, built on the cp-kafka image, creates the topics, and confluent-kafka is the Python client, built on librdkafka.

\subsection*{Database and File Storage}

  For the database we use PostgreSQL, with psycopg, psycopg-binary and postgres-exporter. For image storage we use SeaweedFS, with boto3 and botocore to communicate with the S3 gateway. To generate simulated DDM images, we use numpy, pandas, matplotlib and pillow, with some supporting libraries: argon2-cffi, argon2-cffi-bindings, cffi and pycparser.

\subsection*{Data Movement}

  We experimented with two data transfer tools. etransfer (v2.0, from JIVE) is free and open source, so we compiled it from source at build time. It needs a C++11 compiler, bundles its own UDT and SRT libraries, and listens on port 4004 for commands (TCP) and port 8008 for data (SRT). ExpeDat (\texttt{servedat} 1.23.1, MTP 4.5.3) is proprietary: the vendor ships ready-made binaries, so we copy them into the image at build time, with separate arm64 and x86-64 builds. We ran the 21-day free trial, so production use would need a licence.

\subsection*{Testing and Load Testing}

  For the testing environment we use pytest, pytest-django, pytest-cov and pytest-asyncio, and k6 for load testing in its own container.

\subsection*{Infrastructure and Monitoring}

  We use Traefik to handle HTTPS and UDP routes. We use Docker Desktop and Compose on the development machines. For Portainer, Prometheus and Grafana we used latest-tag images.

\subsection*{Hardware and Hosting}

  We used four droplets with 1 vCPU, 2 GB RAM and 50 GB disk for GBT and VLBA, and one droplet with 4 vCPU, 8 GB RAM and 160 GB disk for DSOC, where we have our database, image storage, ExpeDat server and other containers. One thing worth mentioning is that development was on arm64 (Apple Silicon) while the droplets are x86-64, so the binaries must match.

\section{Ideas for Future Improvements} \label{Future}
%===== Some of these may be resolved in [760] Final Technical Cleanup? Not sure

\begin{itemize}
  \item Features
  \begin{itemize}
    
    \item Originally, DSOC checks its storage and responds to a single VLBA station if it can accept the incoming e-transfer/expedat raw data transfer/stream. Currently, we have this check occurring simultaneously for all 10 VLBA stations. But we noticed that with 10 consecutive storage check requests, DSOC responds yes without taking into account the requests it’s already approved. With the simultaneous transfers/streams, DSOC storage could potentially go over its storage limit for incoming raw data. It would be beneficial to have some logic built in place for DSOC to keep track of its storage before and after each approval of a requested VLBA site's incoming transfer/stream.
    
    \item Currently, on our history events page, you can see that in our sequencing of events, DSOC sends a 'Completed' kafka message 10 times per 10 VLBA sims. It might make more sense to have DSOC wait until it has finished processing all 10 VLBAs raw data, generates its 10 DDM images and stores them to seaweedfs, and then send only one 'Completed' kafka message to be displayed on the UI and communicate to the remote observer that the sequencing of events has finished. 
  
  \end{itemize}
  
  \item Known issues
  \begin{itemize}
    
    \item The submit new waveform button currently unlocks after the first of several concurrent VLBA transfers completes, rather than after all of them have completed.
    \item Part way through the prototype's development we had a big refactor to decouple our UI from the postgres database and convert the UI to be completely event-driven by relying on kafka for updates to the UI rather than polling the database to update the UI. Before this refactor, we had built certain safeguards to ensure that the website, backend processes, and our docker ecosystem could fail gracefully and print helpful logs for debugging and restarting, rather than failing and exiting. We have not tested any of the graceful failure scenarious since the UI Bridge refactor, so it would be valuable to go back through those scenarious and ensure that the prototype fails gracefully. 

  \end{itemize}
\end{itemize}
